Run/Stop y consola

#include <stdio.h>

int main(void) {
    int numero;
    printf("Introduce un numero entero: ");
    int resultado = scanf("%d", &numero);
    if (resultado == EOF) {
        printf("stdin esta vacio.\n");
        return 0;
    }
    if (resultado != 1) {
        printf("Entrada invalida.\n");
        return 0;
    }
    printf("Numero leido: %d\n", numero);
    return 0;
}

El programa escribe el prompt y pausa la misma ejecución hasta que la persona envía una línea; al cerrar stdin explícitamente, la lectura obtiene EOF y sigue la rama de aviso. Botón compacto Run → Stop en main.c, consola debajo del editor y footer de línea/columna visible. Run toma una copia del texto y ejecuta en Worker; la consola decodifica stdout/stderr, conserva salida parcial y muestra el código de salida o un diagnóstico.

API implementada: File en navegador, rutas en Node y preparación reutilizable. El README del paquete documenta la cobertura, los tipos públicos y ejemplos de medición.

P4 conserva las capacidades P1–P3 y añade traducción por macros y directivas, varias unidades de traducción, K&R y funciones variádicas, main() vacío y main(argc, argv), salida por bytes y archivos/streams virtuales. El core publica createExecutionSession para reanudar el mismo VM al recibir stdin; las llamadas existentes a execute mantienen stdin completo y EOF inmediato. Los lectores interactivos son scanf/fscanf/getchar/getc/fgetc/fgets/fread; sscanf sigue leyendo su cadena finita. Los subconjuntos incorporados incluyen assert.h, ctype.h, errno.h, inttypes.h, iso646.h, stdarg.h, stdio.h y string.h. Las familias siguen parciales; stdio mantiene limitaciones publicadas para %a/%A, %lc/%ls y conversiones long double. No se afirma conformidad completa con C11.

long factorial(int n) {
    if (n <= 1) return 1;

    uint64_t exact = 9007199254740993ULL;

#include <stdlib.h>
struct Pair { int left; int right; };
int main(void) {
    int values[3] = { 17, 25, [2] = 0 };
    int *end = values + 3;
    void *opaque = values + 1;
    int *alias = opaque;

Contrato del motor implementado

core.prepare(project) → programa inmutable; core.execute(program) → ejecución síncrona por lotes con stdin cerrado; core.createExecutionSession(program) → sesión reanudable con stdin abierto. El proyecto admite translationUnits; browser y node exponen runProject y conservan runFile. Sin React, DOM ni filesystem del host en el core.

Cada sesión crea objetos, heap, frames, argumentos, streams y archivos virtuales nuevos. ExecuteOptions.io configura argv, bytes iniciales de stdin y archivos semilla. En la sesión interactiva, resume() devuelve el snapshot acumulado antes de esperar; appendStdin(bytes) reanuda la misma llamada y endStdin() cierra la entrada después de los bytes en cola. Un buffer abierto vacío no es EOF; EOF queda sticky. stdout/stderr son Uint8Array incluso con salida parcial tras error o límite. Solo la terminación normal tiene exit code Linux.

Medidas separadas: readMs, prepareMs, executeMs y totalMs del adaptador. En la sesión, executeMs suma setup síncrono y llamadas a resume(), sin medir espera humana. El arranque y comunicación del Worker quedan fuera y pueden medirse desde el padre. Reutilizar el preparado para benchmarks ya es posible; un helper dedicado con calentamiento y muestras sigue pendiente.

Límites de Run: 100.000 caracteres, 25.000 tokens, 1.000.000 pasos de preprocesamiento, profundidad 128 por etapa, 100.000 instrucciones, 1 MiB de memoria C, 1 MiB de E/S virtual y watchdog de 10 segundos. La API acepta presupuestos configurables o null para desactivarlos. El Worker pausa el watchdog mientras espera stdin y lo reanuda al recibir una línea; Stop termina el Worker desde el hilo padre. Los adaptadores comprueban AbortSignal alrededor de la lectura y entre etapas; el core síncrono no procesa nuevos eventos durante la ejecución. Node no crea Workers implícitos.

Debug API · D1 (etapa 1): eventos de ciclo de vida

Contrato cotejado con los tipos y el runtime del core. Esta observabilidad es transversal al motor: no amplía el lenguaje C, la matriz de cobertura ni P5. createDebugSession usa el mismo VM y semántica que createExecutionSession; solo la sesión de depuración recolecta eventos. Los tipos públicos de depuración se exportan desde core; una sesión normal no crea collector ni buffer.

createDebugSession(program: PreparedProgram, options?: ExecuteOptions,
                   debugOptions?: DebugSessionOptions):
  DebugExecutionSession

interface DebugSessionOptions { readonly maxEvents?: number } // default: 100_000
interface DebugExecutionSession {
  resume(): DebugProgress
  appendStdin(bytes: Uint8Array): void
  endStdin(): void
  drainEvents(): readonly DebugEvent[]
}
type DebugProgress = ExecuteProgress | DebugLimitResult

debugOptions solo admite maxEvents; null, claves desconocidas o un valor que no sea un entero seguro no negativo producen un diagnóstico.

Cada evento tiene sequence: number, kind, location: {file, line, column} y frameId/scopeId: number | null. Los kinds son frame-enter, frame-exit, scope-enter, scope-exit, object-create y object-delete; los eventos de frame incluyen functionName: string; los de scope incluyen también scopeName: string, asignado desde el AST. El cuerpo de función usa su nombre y un bloque desnudo usa bloque. Las etiquetas de control son canónicas y no incluyen sus condiciones: if(...), while(...), for(...), do { ... } while (...) y switch(...); else conserva else. El bloque de un for usa bloque de for. Un bloque compuesto de control produce una sola activación y los bloques anidados siguen siendo independientes. frameId y scopeId identifican una activación de función y una de scope, respectivamente. location señala la operación disponible en runtime; retornos y saltos usan la ubicación de su operación. El cierre normal de un bloque informa la ubicación del token } conservado por el parser; los scopes cerrados por return o salto usan la ubicación de esa transición. frame-enter usa la declaración de la función y frame-exit usa el return explícito o, al caer al final, la llave de cierre del cuerpo. Una raíz de objeto describe almacenamiento real de la VM con objectId/allocationId: number, duration, origin, typeSummary: string, addressVirtual: bigint y size: number, además de name?: string cuando existe. Para cada raíz objectId y allocationId son iguales. duration distingue automatic, static, heap y compound-literal; origin distingue variable, compound-literal, heap y string-literal. Arrays y structs emiten una sola raíz: no hay eventos por elemento o miembro ni materialización de subobjetos perezosos. Se incluyen literales de cadena observables por C (sin name); se excluyen objetos de infraestructura como errno, argv y el almacenamiento interno de va_list.

resume() devuelve DebugProgress. Los objetos de duración automática y los compound literals de bloque pertenecen a una activación y terminan al salir de su scope; los de heap terminan al liberarlos con free. En create/delete, frameId/scopeId señalan el dueño del lifetime para automáticos y compound literals; son nulos para heap, estáticos y literales de cadena. Los objetos estáticos y los literales se crean una vez por sesión y no reciben eliminación sintética al terminar el programa. Las celdas locales automáticas se reservan internamente al entrar al scope, pero object-create y el snapshot se publican al ejecutar la declaración; los parámetros se publican al entrar en la función. object-delete solo se emite para IDs que ya tuvieron creación. D1 traza objetos del runtime actual, no es un inventario estático de todas las declaraciones C: los estáticos locales se crean al alcanzar su scope, así que una función o bloque no alcanzado no emite evento. Los eventos globales pueden emitirse al construir la sesión, antes del primer resume(). drainEvents() devuelve lo acumulado desde el drain anterior, en orden de secuencia.

maxEvents cuenta los eventos de toda la sesión y no se reinicia al drenar. Al excederlo, la sesión devuelve kind: 'debug-limit', resource: 'maxDebugEvents', con limit, diagnósticos, métricas, stdout y stderr. Conserva el prefijo y comprueba el límite antes de mutar el estado que produciría el evento excedente. Este resultado pertenece a DebugProgress; los resultados y LimitResource de ejecución normales no cambian.

D1 solo informa ciclos de vida; no incluye UI, MemoryViewer, inspector ni snapshots de valores, stepping o historial. Etapas futuras: inspección de solo lectura con límites de fuente, avance paso a paso e historial/reversa con snapshots. No se anuncian como implementadas.

Perfil implementado y objetivo

P1–P4 implementan _Bool/char de 1 byte, short de 2, int de 4 y long/long long de 8, float binary32 de 4 bytes, double binary64 de 8 y punteros virtuales de 64 bits (8 bytes, alineación 8). Char firmado y complemento a dos; enteros exactos con BigInt, unsigned módulo 2^N, narrowing firmado por low bits y right shift firmado aritmético. Float redondea al formato de destino tras operaciones/conversiones y FLT_EVAL_METHOD vale 0. Se conservan NaN, infinitos, subnormales y cero negativo, sin afirmar Annex F. Math usa el host sin prometer redondeo correcto universal. Punteros se representan por identidad de objeto y offset; aritmética/resta se limita a un array, one-past no se desreferencia y void* solo transporta direcciones de objeto. El layout de agregados usa alineación LP64, los miembros anónimos comparten el layout de su struct/union contenedor y los bytes siguen little-endian; bit-fields, miembros flexibles, long double binary80, offsetof y max_align_t quedan pendientes.

Operandos y argumentos se evalúan de izquierda a derecha donde C permite un orden no especificado, sin legalizar accesos sin secuenciar. El UB detectado detiene la sesión con diagnóstico; no se promete detección universal. maxMemoryBytes/peakMemoryBytes cuentan todos los bytes virtuales vivos de parámetros, locales, globals/estáticos, literales de cadena y heap, sin medir la memoria JavaScript. Pilas explícitas permiten recursión profunda con límites desactivados; límites de instrucciones/profundidad detienen bucles y recursión infinitos.

VLA, complejos, atomics y threads se anuncian por capacidad; TLS tiene seguimiento propio. Annex F/G y Annex K se evalúan aparte. Cobertura por versión, sin afirmar conformidad completa durante fases parciales.

C11 estricto sigue siendo el objetivo, no una afirmación de conformidad. POSIX, GNU, syscalls, ELF, assembly y código máquina x86 necesitan otra hoja de ruta. P4 ya muestra salida stdout/stderr decodificada; los puertos de reloj, entorno y señales siguen pendientes.

Fuentes: WG14 N1570, GCC Standards, GCC x86, psABI x86-64 y Linux exit(3). P1/P2 están implementados; P3 y P4 están implementados parcialmente, y P5/P6 siguen pendientes. Las familias conservan capacidades y casos de aceptación pendientes.
